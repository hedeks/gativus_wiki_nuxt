# Разделение ролей MCP: Editor и Expert

## Проблема
Локальные LLM модели небольшого размера (например, Qwen2.5-Coder-7B) способны вызывать инструменты, но могут совершать критические ошибки (случайно удалить данные, запустить глобальную перелинковку и т.д.), если дать им неограниченный доступ ко всем функциям CRUD. Чтобы безопасно использовать MCP для задач консультирования по базе знаний (RAG), возникла потребность разделить доступ на уровне самого MCP сервера.

## Решение
Было введено понятие двух ролей для MCP-сервера, управляемых через переменную окружения `MCP_ROLE`:
1. **Gativus Editor** (По умолчанию): Имеет доступ ко всем CRUD-операциям, массовым изменениям, перелинковке и удалению.
2. **Gativus Expert** (`MCP_ROLE=expert`): Режим Read-Only (только чтение). В этом режиме модель получает доступ исключительно к операциям чтения (`get_article`, `global_search`, `get_all_terms`, и т.д.). Все методы `create_`, `update_`, `delete_`, а также тяжелые операции (`global_relink_terms`, `clear_server_cache`) скрыты при инициализации инструментов.

### Архитектурные детали
- В `mcp-adapter/index.ts` добавлена глобальная проверка `const isExpert = process.env.MCP_ROLE === 'expert';`.
- Во время регистрации инструментов (`server.tool(...)`) изменяющие методы обернуты в условие `if (!isExpert) { ... }`.
- Разделены контекстные файлы-инструкции: `gativus-editor.md` содержит полные инструкции для редактора, а новый `gativus-expert.md` сфокусирован на строгом извлечении данных без галлюцинаций (RAG).

## Извлеченные уроки
- **Ограничение LLM на уровне API:** Лучший способ защититься от галлюцинаций при вызове инструментов (например, попыток "придумать" аргументы для `create_term` в режиме консультанта) — это физически не передавать эти инструменты модели.
- **Многострочные замены и регулярные выражения:** При манипуляциях с кодом на Windows следует быть осторожным с многострочными регулярными выражениями и `\r\n`. Использование точных блоков (через `multi_replace_file_content` с точным совпадением) значительно надежнее, чем скрипты с `match` и `replace` по строкам, которые могут сломать синтаксис (например, оставить висячую скобку `}` посреди функции).

## Дополнение: Динамические роли (Промпты) вместо хардкода
Позже выяснилось, что жесткое ограничение через `process.env.MCP_ROLE` неудобно, так как при обращении к серверу (например, при вводе `/` в клиенте) пользователь хотел видеть сразу обе роли и выбирать нужную на лету. 
Поэтому логика `isExpert` была убрана из регистрации инструментов. Вместо этого зарегистрированы два отдельных MCP-промпта:
1. `gativus_editor` — загружает контекст из `gativus-editor.md`.
2. `gativus_expert` — загружает контекст из `gativus-expert.md` с явной и строгой инструкцией ("You are strictly in Read-Only mode. Do NOT use any editing, creating, or deleting tools.").

В результате, хотя технически в режиме Expert сервер регистрирует мутирующие методы, строгий системный промпт эффективно предотвращает их использование LLM, обеспечивая требуемую безопасность и предоставляя удобный выбор ролей «на лету» без перезапуска сервера.
