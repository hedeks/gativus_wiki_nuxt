# Ошибка 401 и блокировка навигации (Nuxt Suspense + Auth Interceptor Deadlock)

## Проблема
Пользователь обратился с проблемой: при клиентской навигации между статьями (по маршрутам вида `/articles/[slug]`) происходила "аномально долгая загрузка". Страница визуально зависала на старом контенте, несмотря на то, что URL в адресной строке уже изменился. Пользователь также приложил ошибку из консоли: `Failed to load resource: the server responded with a status of 401 () https://gativus.com/api/user/bookmarks`.
При этом, если открыть ссылку на новую статью в новой вкладке (через SSR), страница загружалась мгновенно и без зависаний.

## Решение
Проблема заключалась в связке встроенного механизма Nuxt 3 `<Suspense>` и клиентского плагина-интерцептора для авторизации (`plugins/api.client.ts`). 

В компоненте `[slug].vue` вызывался хук для загрузки закладок:
```typescript
const { data: bookmarkedIds, refresh: refreshBookmarks } = useFetch<number[]>('/api/user/bookmarks', {
  headers: store.getAuthHeader(),
  server: false,
})
```
Для неавторизованных пользователей этот запрос возвращал статус 401. 
В проекте настроен глобальный перехватчик `globalThis.$fetch` (в `plugins/api.client.ts`), который при получении 401 ошибки ставит промис на паузу (помещает его в `requestQueue`) и вызывает модальное окно повторной авторизации (`store.startReauth()`). Промис остаётся в подвешенном состоянии (`pending`) до тех пор, пока пользователь не авторизуется.

Nuxt 3 использует `<Suspense>` для управления клиентской навигацией. Это означает, что роутер **ждёт** разрешения всех асинхронных вызовов (`useFetch`, `useAsyncData`) в функции `setup()` перед тем, как завершить переход и отрисовать новый компонент. Так как промис получения закладок бесконечно висел в очереди интерцептора, `<Suspense>` блокировал переход. Визуально это выглядело как намертво зависшая страница.

Для исправления ситуации вызов `useFetch` был модифицирован так, чтобы он не отправлялся автоматически для неавторизованных пользователей:

```typescript
const { data: bookmarkedIds, refresh: refreshBookmarks } = useFetch<number[]>('/api/user/bookmarks', {
  headers: store.getAuthHeader(),
  server: false,
  immediate: store.isLoggedIn,
  watch: [() => store.isLoggedIn]
})
```

## Извлеченные уроки (Ловушки)
1. **Nuxt Suspense и Promise Queue**: Будьте крайне осторожны с реализацией очередей промисов (Promise Queue) в интерцепторах API. Если асинхронный запрос вызывается на верхнем уровне `<script setup>` (через `useFetch` или `await useAsyncData`), и ваш интерцептор не отклоняет (`reject`) промис при ошибке, а ставит его на "бесконечную" паузу, это приведёт к "deadlock" состояния `<Suspense>`. Клиентская навигация в приложении перестанет работать без каких-либо явных ошибок в консоли Vue/Nuxt.
2. **Разница между SSR и CSR (Client-Side Routing)**: При первичном открытии страницы в браузере (SSR) `useFetch` с параметром `server: false` запускается в фоне уже после монтирования компонента (`onMounted`), поэтому он не блокирует отрисовку. Но при переходе на эту же страницу через `<NuxtLink>` (клиентский роутинг) тот же самый `useFetch` рассматривается как часть Suspense Boundary и блокирует отображение новой страницы до своего завершения (или падения).
3. **useRequestHeaders на клиенте**: Использование `useRequestHeaders` имеет смысл только в SSR-контексте для проброса заголовков от клиента к серверу. На стороне браузера он возвращает пустой объект `{}`, поэтому токены авторизации нужно брать напрямую из хранилища (Pinia) или cookie.
